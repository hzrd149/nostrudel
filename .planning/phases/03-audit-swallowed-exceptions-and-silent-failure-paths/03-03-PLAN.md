<objective>
Make eight best-effort failure paths log their cause through the namespaced debug logger (D-10, D-12),
leaving every one's control flow untouched.

Purpose: These eight account for 8 of the 31 error-severity findings (D-01). Every one of them has
code AFTER the catch block that must still execute — a pending-map cleanup, an effect-cleanup
registration, a fallback JSX return, a `setLoading(false)`, a manual-payment modal, the next loop
iteration. Adding an explicit `return` would be a real bug at each. The correct remedy is D-10's
"log the cause and stay silent": the fallback itself is the handling, and the cause becomes
recoverable when someone investigates.

Output: Eight modified files, zero new files, five new module-private logger constants.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| remote LNURL endpoint → fetchMetadata | Untrusted JSON from a remote lightning address |
| WebLN provider → invoice-modal-provider / inline-invoice-card | Browser extension mediates a payment |
| localStorage → use-cache-form | Locally persisted form JSON is parsed |
| native camera → qr-code-scanner-button | Scanned barcode payload enters the app |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-08 | Information Disclosure | Five new `logger.extend` log calls | low | mitigate | Log only the caught Error plus an already-user-visible identifier (an LNURL address, a zap recipient pubkey, a fallback module name). Never log an invoice preimage, a payment secret, a cached form's field values, or a scanned barcode payload. `logger` is the `debug` package: silent in production unless the namespace is explicitly enabled. |
| T-03-09 | Repudiation | Payment failures previously discarded without trace | low | mitigate | This is the plan's purpose: `inline-invoice-card`, `pay-step` and `invoice-modal-provider` failures now leave a namespaced log entry, so a "payment silently did nothing" report becomes investigable. No user-facing behavior change, per D-10. |
| T-03-10 | Denial of Service | `event-cache` fallback loop and `pay-step` invoice loop | medium | mitigate | An early exit added inside either catch would abort the remaining fallbacks / invoices. The action forbids any control-flow statement and acceptance criteria assert that `return null;` and `setPayingAll(false)` remain reachable, so the loops cannot be truncated. |
| T-03-11 | Tampering | Console channel bypass | low | mitigate | An acceptance criterion runs a jq check for `ai-slop/console-leftover` across the five files and requires `0`, enforcing D-12's logging channel rather than trusting review. |

No new attack surface: no new network call, dependency, parser or exported API. ASVS L1 — remote input
handling at these boundaries is unchanged; only observability is added.
</threat_model>
