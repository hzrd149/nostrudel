<interfaces>
From src/hooks/use-async-action.ts (the full contract — 29 lines):
```typescript
export default function useAsyncAction<Args extends Array<any>, T = any>(
  fn: (...args: Args) => Promise<T>,
  deps: DependencyList = [],
): { loading: boolean; run: (...args: Args) => Promise<T | undefined> };
```
Behavior: sets `loading` true, awaits `fn`, and on throw does
`if (e instanceof Error) toast({ description: e.message, status: "error" })` then logs. Returns
`{ loading, run }`.

Critical mechanic: the hook stores `ref.current = fn` on every render, so the latest closure is always
called regardless of the `deps` array — `deps` only affects the identity of `run`. This is why the
`deps` values specified below are both correct and safe even though none of the three components
memoizes its handler today.

Props of the two near-identical components (unchanged by this plan):
```typescript
{ url: string; onRemove: () => void | Promise<any>; details?: ReactNode }
```
</interfaces>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user click → destructive action | A user-initiated removal or full cache wipe crosses from UI into storage/state mutation |
| thrown Error → toast | An Error's `message` is rendered into the UI by the hook |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-03-12 | Information Disclosure | `useAsyncAction` toasting `e.message` on the three converted handlers | low | accept | The hook only toasts when `e instanceof Error`, and these three actions throw application errors (removal/wipe failures), not credential or key material. This is the pattern `AGENTS.md` already marks REQUIRED across the codebase, so this plan adds no new class of exposure. |
| T-03-13 | Repudiation | Destructive actions failing with no feedback | medium | mitigate | This is the plan's purpose. Before the change a failed mint removal, relay removal or database wipe produced no toast and no log, so a user could believe a destructive action succeeded when it had not. The conversion surfaces the failure via toast and logs it. |
| T-03-14 | Denial of Service | Button stuck in a loading state after conversion | low | mitigate | The hook clears `loading` on both the success and failure paths. `pnpm build` catches a missed render call site at compile time (deleting `loading` breaks the old reference), and the Task 3 checkpoint confirms spinner behavior visually. |

No new attack surface: no new network call, dependency, parser or exported API. The `enable-with-delete`
wipe is equally destructive before and after; no new confirmation step is removed. ASVS L1.
</threat_model>
