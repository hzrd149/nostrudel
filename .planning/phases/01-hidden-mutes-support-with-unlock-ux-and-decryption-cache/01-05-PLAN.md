<objective>
Surface the auto-unlock preferences in the Privacy settings section: a master unlock-all option, and — only while that is unchecked — one option per registered pending-unlock category.

Purpose: D-04 places these controls in Privacy settings specifically; D-05 requires the per-category list to be driven by the registry so no dead or placeholder categories are shown for sources that are not wired this phase. Together they make the auto-unlock preference that plan 01-01's driver reads user-controllable, and give the user a way to turn off what plan 01-04's "Enable auto-unlock" button switched on.

Output: a new auto-unlock settings group in `src/views/settings/privacy/index.tsx`.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → device storage (Capacitor Preferences) | These switches are the user-facing control over whether the app initiates signer decrypt traffic without a click. |
| settings UI → auto-unlock driver | A preference written here changes non-interactive behaviour at the next app start. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-15 | Elevation of Privilege | unlock-all switch | high | mitigate | A user who enables blanket auto-unlock without understanding it consents to signer decrypt requests on every load, which is the habituation half of the signer-prompt-fatigue threat. Mitigated by defaulting off (D-01), by requiring an explicit toggle, by helper text that states the app will ask the signer to decrypt at start rather than framing it as a convenience, and by the plan 01-01 driver capping attempts at one per category per account per app session. |
| T-01-16 | Tampering | per-category preference map | low | accept | A local attacker could flip stored entries to enable auto-unlock. Accepted for the same reason as T-01-02: that attacker already holds the session and its signer access. The UI only ever writes through `setAutoUnlockCategory`, which replaces the map immutably, and the stored value is defensively parsed on read. |
| T-01-17 | Spoofing | category labels rendered from the registry | low | mitigate | Labels come from registered category descriptors rather than from network data, and every registration in this phase is a static in-repo module. No relay-supplied or user-supplied string reaches this list, so there is no injection surface; keep it that way by not adding dynamic registration from event content. |
| T-01-SC | Tampering | npm/pnpm installs | high | mitigate | No new packages; all imports are `@chakra-ui/react`, `applesauce-react`, and local modules. No install command may appear in this plan's commits. |
</threat_model>
