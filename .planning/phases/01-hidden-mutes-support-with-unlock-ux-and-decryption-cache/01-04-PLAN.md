<objective>
Build the application-wide pending-unlock affordance in the side nav — the single visible signal D-07 relies on, and the thing D-02 describes: an indicator showing that things are pending unlock, offering both unlock-once and enable-auto-unlock.

Purpose: without this, the registry from plan 01-01 and the categories from plan 01-03 have no user-facing entry point, and D-09's promise that the cache password is reachable outside the Messages route does not hold.

Output: a collapse-aware nav button with a count badge, a modal listing every pending category with its own action, and the wiring into both the desktop rail and the mobile drawer.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| user → app → signer | The nav affordance is the only place in the app that can initiate a batch of decrypt prompts from a single click. |
| user → password field | The decryption-cache category's password form is surfaced here, so the cache password crosses this UI. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-11 | Elevation of Privilege | "Unlock now" batch action | high | mitigate | A batch that keeps prompting after the user refuses trains blind approval and, with many categories, becomes a prompt flood. Mitigated by `unlockPendingCategories` (plan 01-01) rethrowing immediately on a signer-refusal-shaped error so the batch stops at the first refusal, and by this phase registering only two categories (D-03). |
| T-01-12 | Information Disclosure | error toasts from failed unlocks | medium | mitigate | Toast text must not carry decrypted content or internals. Mitigated by routing every action through `useAsyncAction`, which renders only `Error.message`, and by the modal adding no catch block and no custom error formatting of its own. |
| T-01-13 | Spoofing | cache password field rendered inside the nav modal | medium | mitigate | A password field in a new location invites entry into a look-alike surface. Mitigated by rendering the category's own registered `unlockComponent` (built in plan 01-03 on `EncryptedStorage.unlock`) rather than a second password implementation, so there is exactly one code path that ever sees the cache password. |
| T-01-14 | Denial of Service | auto-unlock enabled from the modal | low | accept | Enabling auto-unlock makes future app starts issue decrypt requests without a click. Accepted: it is an explicit, user-initiated opt-in (D-02), it is bounded to one attempt per category per account per session by the plan 01-01 driver, and it is reversible from Privacy settings (D-04). |
| T-01-SC | Tampering | npm/pnpm installs | high | mitigate | No new packages; all imports are `@chakra-ui/react`, `applesauce-react`, `react`, and local modules. No install command may appear in this plan's commits. |
</threat_model>
