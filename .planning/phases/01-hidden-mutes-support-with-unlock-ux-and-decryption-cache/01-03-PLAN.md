<objective>
Register the phase's two pending-unlock sources against the registry built in plan 01-01: the user's mute list (D-03 — the only source wired this phase) and the decryption cache's own lock (D-09). Registering the cache lock is what makes the phase's headline promise — unlock once, stay unlocked across reloads — actually hold on default settings, because `encryptDecryptionCache` defaults to true and its password is today only ever prompted inside the Messages route.

Purpose: D-03 requires mutes to be the first and only registered source; D-09 requires the cache lock to be a pending item in the same mechanism; D-06 requires a cross-device replacement to fall back to pending without auto re-unlocking.

Output: two registration modules under `src/services/`, one self-contained password form component, and their eager import at app init.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → signer | `unlockHiddenMutes` issues a NIP-04 decrypt through the active account's signer. |
| relays → app | A kind-10000 replacement can arrive from any device holding the user's key; the app must not treat a new version as equivalent to the previously unlocked one. |
| app → IndexedDB (decryption cache) | Decrypted hidden-mute plaintext is persisted locally by the pre-existing `persistEncryptedContent` subscription. |
| user → password field | The cache password crosses from the user into `EncryptedStorage`'s key derivation. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-07 | Tampering | cross-device mute-list replacement | high | mitigate | A replacement published from another (possibly compromised) device could quietly change the hidden mute set. Mitigated by D-06: the replacement has a new event id, misses the decryption cache, and returns the category to pending. The registration module adds no "has unlocked before" flag and no automatic re-unlock, so a changed list always requires a fresh, deliberate unlock. |
| T-01-08 | Information Disclosure | decrypted hidden mutes persisted in IndexedDB | high | mitigate | Decrypted mute plaintext at rest could be read by anything with local storage access. Mitigated by the pre-existing `EncryptedStorage` wrapper, which `encryptDecryptionCache` enables by default. This plan adds no new persistence path — it explicitly does not modify `src/services/decryption-cache.ts` — so hidden-mute plaintext travels the same encrypted-at-rest route as every other cached decryption. |
| T-01-09 | Spoofing | cache password form | medium | mitigate | A weakened or re-implemented password check could accept an incorrect password and produce garbage plaintext. Mitigated by reusing `EncryptedStorage.unlock(password)` and `require-decryption-cache.tsx`'s exact validation and failure toasts; the form implements no comparison, no derivation, and no crypto of its own (ASVS V5 marginal, V6 hand-off only). |
| T-01-10 | Elevation of Privilege | mutes category unlock on a read-only account | low | mitigate | Attempting a signer operation on a `ReadonlyAccount` would surface a confusing internal error. Mitigated by `canUnlock$` reporting false for those accounts (consumers disable the action) and by `unlock` throwing an explicit, descriptive error if it is reached anyway. |
| T-01-SC | Tampering | npm/pnpm installs | high | mitigate | No new packages. All imports resolve to `applesauce-core`, `applesauce-common`, `applesauce-accounts`, `rxjs`, `nostr-tools`, and `@chakra-ui/react`, already direct dependencies. No install command may appear in this plan's commits. |
</threat_model>
