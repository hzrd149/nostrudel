<objective>
Build the generic, application-wide pending-unlock registry service and the two auto-unlock preferences it is driven by. This is the foundation every other plan in this phase consumes: the side-nav affordance, the Privacy settings toggles, the mute-list category, the decryption-cache category, and the Muted view's Private section all read their locked state from this one registry.

Purpose: D-02 requires one generic mechanism (not a mute-specific control) and D-05 requires the Privacy settings category list to be driven by whatever registers itself. Both demand a registry with a stable category descriptor shape before any source or UI can be written.

Output: `src/services/pending-unlock.ts` (new registry service, including the preference-gated auto-unlock driver) and two new `PreferenceSubject` entries in `src/services/preferences.ts`.
</objective>

  <action>
    Create `src/services/pending-unlock.ts` as a module-scope RxJS registry singleton, following `decryption-cache.ts`'s idiom exactly (no React, no Chakra, no toasts).

    Export the category descriptor type `PendingUnlockCategory` with these fields:
    - `id: string` — stable identifier, also used as the key into `localSettings.autoUnlockCategories`.
    - `label: string` — human-readable name shown in the nav popover and in Privacy settings.
    - `description?: string` — optional one-line explanation for the Privacy settings helper text.
    - `count$: Observable<number>` — number of pending-locked items for the active account; `0` when nothing is pending.
    - `canUnlock$: Observable<boolean>` — `false` when the active account/session cannot perform the unlock (for example a signer-less account). Consumers show the pending indicator regardless and disable the action.
    - `unlock: () => Promise<void>` — unlocks everything pending in the category. It MUST let errors propagate (throw). It MUST NOT catch-and-toast; `useAsyncAction` at the call site is the single toast site (D-08).
    - `unlockComponent?: ComponentType<{ onUnlocked?: () => void }>` — optional self-contained unlock UI for categories that need extra user input (for example a password field). Import `type ComponentType` from `react` as a type-only import so this stays a plain `.ts` module. A category that defines `unlockComponent` is never auto-unlocked and is never included in the batch unlock.

    Also export the derived row type `PendingUnlockState` with fields `category: PendingUnlockCategory`, `count: number`, `canUnlock: boolean`.

    Implement and export:
    - A module-private `BehaviorSubject<PendingUnlockCategory[]>` seeded with `[]`.
    - `registerPendingUnlockCategory(category: PendingUnlockCategory): () => void` — appends the category (replacing any existing entry with the same `id`) and returns an unregister function that removes it by `id`.
    - `pendingUnlockCategories$: Observable<PendingUnlockCategory[]>` — the registry as a read-only observable.
    - `pendingUnlockState$: Observable<PendingUnlockState[]>` — `switchMap` over the categories; when the array is empty emit `[]` via `of([])` (never call `combineLatest` on an empty array, it does not emit); otherwise `combineLatest` each category's `count$` and `canUnlock$` into the row shape. End with `shareReplay(1)`.
    - `pendingUnlockTotal$: Observable<number>` — `pendingUnlockState$` mapped to the sum of `count`, `shareReplay(1)`.
    - `autoUnlockEnabled$(id: string): Observable<boolean>` — `combineLatest` of `localSettings.autoUnlockAll` and `localSettings.autoUnlockCategories`, mapped to `all === true || map[id] === true`, with `distinctUntilChanged()`.
    - `isAutoUnlockEnabled(id: string): boolean` — the same rule read synchronously from the two subjects' `.value`.
    - `setAutoUnlockCategory(id: string, enabled: boolean): Promise<void>` — writes an updated copy of the `autoUnlockCategories` map through `localSettings.autoUnlockCategories.next(...)` (never mutate the existing object in place; `PreferenceSubject.next` is async and must be awaited).
    - `unlockPendingCategories(): Promise<void>` — reads the current `pendingUnlockState$` value once (via `firstValueFrom`), filters to rows where `count > 0`, `canUnlock` is true, and `category.unlockComponent` is undefined, then awaits each `category.unlock()` in sequence. Error policy: if a caught `Error`'s lowercased message contains the signer-refusal substring used by `pending-decryption-alert.tsx`, rethrow it immediately so the batch stops rather than firing another signer prompt; for any other error, `console.error` it, keep it as the first-seen failure, and continue the loop; after the loop, throw the first-seen failure if there was one. Never toast here.

    Subscribe to `pendingUnlockTotal$` at module scope to keep the aggregate warm, mirroring `decryptionCache$.subscribe()`.
  </action>

    Append a module-scope auto-unlock driver to `src/services/pending-unlock.ts`. It is the only place in the codebase that may call `category.unlock()` without a click, and it is gated so that it does nothing at either preference's default.

    Behavior:
    - Keep a module-private `Set<string>` of already-attempted `${accountId}:${categoryId}` pairs.
    - Drive from `accounts.active$` piped through `distinctUntilChanged` comparing `account?.id`. On every distinct account (including `undefined`), clear the attempted set — this is the "explicit account switch" trigger. The first emission at app start is the "app start" trigger.
    - For a defined account, `switchMap` into `pendingUnlockState$`; for `undefined`, switch to `EMPTY`.
    - On each emitted state array, for every row where `count > 0`, `canUnlock` is true, `category.unlockComponent` is undefined, `isAutoUnlockEnabled(category.id)` is true, and the `${accountId}:${categoryId}` key is not already in the attempted set: add the key to the set BEFORE awaiting, then call `category.unlock()` and `console.error` any rejection. Never rethrow from the driver — there is no call site to toast it.

    The attempted-set guard is load-bearing for two requirements. It satisfies D-06 (a mute list replaced from another device mid-session returns to locked and waits for the user — no automatic re-unlock), and it mitigates the signer-prompt-fatigue threat identified in RESEARCH.md by making at most one signer prompt per category per account per app session.

    Subscribe to the driver at module scope. Do not add any other unlock trigger anywhere in this file.
  </action>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → signer (NIP-07 extension / nostr-connect / local key) | Every decrypt request crosses out of the app into a user-controlled signer that prompts the user. Volume and timing of these prompts is a security-relevant property. |
| app → device storage (Capacitor Preferences) | Auto-unlock preferences persist across sessions and change whether the app initiates signer traffic on load. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-01 | Elevation of Privilege | auto-unlock driver in `src/services/pending-unlock.ts` | high | mitigate | Signer-prompt fatigue: repeated automatic decrypt prompts train the user to approve blindly. Mitigated by D-01 (both preferences default `false`, so zero automatic calls out of the box) plus the attempted-set guard limiting the driver to one attempt per category per account per app session — triggered only by app start or an explicit account switch, never by a mute-list update. |
| T-01-02 | Tampering | `autoUnlockCategories` preference map | low | accept | A local attacker with device access could flip the stored map to enable auto-unlock. Accepted: the same attacker already has the app's full session and its signer access; this preference grants no capability the attacker lacks. Value is written only through `PreferenceSubject.next` and is defensively parsed (`safeParse`, non-object falls back to `{}`) so a corrupt value cannot crash the service. |
| T-01-03 | Information Disclosure | `unlockPendingCategories` error path | medium | mitigate | An unlock failure must not leak decrypted content or a stack trace into a user-facing toast beyond the `Error.message` the app already surfaces. The service throws the original `Error` and performs no formatting; `useAsyncAction` (existing, unchanged) is the single toast site and renders only `e.message` (D-08). |
| T-01-SC | Tampering | npm/pnpm installs | high | mitigate | No new packages are added in this plan or anywhere in this phase; RESEARCH.md § Package Legitimacy Audit records the phase as not-applicable. No `pnpm add` / `npm install` command may appear in any commit for this plan — if one becomes necessary, stop and escalate for a blocking human legitimacy check. |
</threat_model>
