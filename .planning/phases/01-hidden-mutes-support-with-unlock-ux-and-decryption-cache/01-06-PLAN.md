<objective>
Give private mute entries their own section in the Muted view: a locked placeholder with its own Unlock button while the hidden half is locked, and a list of privately-muted pubkeys once it is unlocked — with a Remove button that actually works.

Purpose: D-10 requires a separate Private section rather than an inline badge or tabs; D-11 requires that section to carry its own Unlock affordance and to show no count while locked; D-12 scopes it to pubkeys only; D-13 and D-14 require that anything removable in that section really is removable from the hidden half.

Output: two new mute models, a small registry-reading hook, the row component extracted for reuse, the Private section component, and the reworked Muted view.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| app → signer | The Private section's Unlock button initiates a decrypt, and its Remove button initiates a re-encrypt of the hidden tag set. |
| app → relays | Removing a private entry publishes a replacement kind-10000 event carrying the whole re-encrypted hidden half. |
| decrypted hidden mutes → rendered DOM | Private mute pubkeys are decrypted content displayed on screen. |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-01-18 | Information Disclosure | locked placeholder | medium | mitigate | Showing a count while locked would leak the size of the private mute list without any decryption — metadata the user chose to encrypt. Mitigated by D-11: the placeholder shows only that hidden content exists (`hasHiddenTags`) and renders no number and no placeholder rows in the locked state. |
| T-01-19 | Tampering | Remove on a Private row | high | mitigate | A hidden-half removal that started from stale or partial plaintext could drop other private entries from the republished ciphertext. Mitigated by delegating to applesauce's `UnmuteUser(pubkey, true)`, whose `modifyHiddenTags` unlocks the current hidden tags before modifying them; this plan writes no tag manipulation and no encryption of its own. The rows are only reachable in the unlocked state, so the extra decrypt round trip described in RESEARCH.md Pitfall 3 does not occur and one signer call is expected. |
| T-01-20 | Repudiation | Remove on a row whose half is mismatched | high | mitigate | A row rendered from the merged model would call `UnmuteUser` without the hidden flag and publish an unchanged list while telling the user it was removed. Mitigated structurally: the public list is sourced from `PublicMutesQuery` and the private list from `HiddenMutesQuery`, so each row's `hidden` flag is fixed by construction rather than guessed (D-13/D-14). |
| T-01-21 | Denial of Service | unvirtualized Private list | low | accept | A user with thousands of private mutes would render thousands of rows at once. Accepted under RESEARCH.md Assumption A3 (private lists are expected to be small), bounded by `maxH` with scrolling, and flagged in a code comment naming the swap to a bounded `FixedSizeList` if the assumption fails. No data exists in this codebase on real-world private mute list sizes. |
| T-01-SC | Tampering | npm/pnpm installs | high | mitigate | No new packages; `react-window`, `react-virtualized-auto-sizer`, `applesauce-actions`, `applesauce-common`, and `applesauce-core` are already direct dependencies. No install command may appear in this plan's commits. |
</threat_model>
