mining progress appears and no note is ever published. The cause is diagnosed and settled: on the
PoW path the draft is never created, so the render gate that mounts `<MinePOW>` can never open.

D-12 at all — this plan does not change D-12's implementation, it makes D-12's behaviour reachable.
Output: three surgical edits, three atomic commits, and an honest statement of what could not be
proven without a human.

**The defect, in one sentence.** `draft` has exactly one writer (`setDraft`, inside `createDraft`),
`createDraft` has exactly one caller, and that caller sits inside the `difficulty === 0` branch — so
on the PoW path `draft` stays `undefined` and the render gate `if (miningTarget && draft)` never
opens. `<MinePOW>` is the only component that renders mining progress *and* the only caller of
`publishPost` on that path, which is why one cause produces both halves of the symptom.

**This is not a Phase 4 regression.** It was introduced 2025-06-02 in `124345b25`, which deleted the
throttled `useAsync(() => getDraft())` that had been incidentally populating `draft`. The pre-Phase-4
snapshot of the file is byte-identical at the same line numbers. It is routed here by user decision.
The full diagnosis is in `.planning/debug/pow-mining-never-starts.md`.

**Site 1 — `src/views/new/note/short-text-form.tsx`, `submit` at lines 144-155.** Wrapped in
`try { … } finally { setLoading(""); }`. The PoW branch at line 146 calls only
`setMiningTarget(values.difficulty)`; the `else` branch sets a loading message, calls
`createDraft(values)` at line 149 and awaits `publishPost(unsigned)`. `setDraft(unsigned)` is at
line 119, inside `createDraft`. The render gate is at line 176.

**Site 2 — `src/components/post-modal/index.tsx`, `submit` at lines 145-148.** The identical defect
in a different shape, and the difference matters: **this file's `submit` has no `try`/`finally`
wrapper and this component has no loading state at all** — there is no `setLoading` anywhere in the

and `else publishPost(await createDraft(values));` (the existing call is not awaited). `setDraft` is

**Those two files are the complete PoW surface.** `MinePOW` is imported and rendered in exactly two

**Site 3 — `src/components/pow/mine-pow.tsx` line 120.** The ternary that chooses between the
"Found POW" success screen and the "Mining POW..." progress screen compares `bestProgress.difficulty`
against `targetPOW` with a **strict** greater-than. The worker breaks at `difficulty >= target`
(`src/components/pow/miner.ts:25`), so the overwhelmingly common outcome is a difficulty landing
*exactly* on the target. With a strict comparison the success branch is therefore almost never
taken: the user watches the progress screen for the full 800 ms `successDelay` and then the note
posts anyway. Changing the operator to greater-than-or-equal makes the display agree with the
worker's own termination condition.

**D-12 is exonerated and line 47 must not be touched.** `cleanup();` at line 47 sits lexically
inside `handleMessage`, in the `msg.type === "complete"` branch, and runs only after
`onComplete(msg.draft)` at line 45 has already captured the mined draft. The worker spawn loop at
lines 51-59 never reaches it. It was the prime suspect and was positively ruled out. Any edit to
line 47 is wrong.
