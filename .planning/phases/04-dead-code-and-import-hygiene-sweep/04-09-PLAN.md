**Six of these are safe mechanical rewrites** — the double negation, the same-name rename, the two
spreads and the two parameter-property assignments. They have no behavioural edge case worth
guarding.

**Three need real care and are split into their own task.** Shadowing a restricted global is fixed
by renaming a binding, which ripples to every reference and possibly to importers if the shadowed
name is exported. Replacing a single-argument `new Array(n)` changes whether the result is a sparse
or dense array, which matters if the code later maps over it. A "useless" length check is only
useless when the value cannot be null or undefined, and removing a guard that was protecting against
that changes behaviour.

D-08 governs any site where the correct fix would change behaviour: keep the code and add a
rule-scoped ignore naming the rule and ending with a reason that justifies why it could not be fixed.
Any such ignore is a new Documented Ignores Ledger row beyond 04-VALIDATION.md's four, and must be
reported for 04-11 to record.
