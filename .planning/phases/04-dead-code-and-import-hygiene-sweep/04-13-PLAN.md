**CR-03 — the timeout handle is discarded.** `mine-pow.tsx` line 111 schedules the publish with
`setTimeout` and throws the handle away. `successDelay` defaults to 800 ms (line 92). There is exactly
**one** `setTimeout(` call in this file. Combined with CR-02's missing teardown, an unmount inside
that window still fires the callback, which is `publishPost` — closing over `publish` (a context
callback) and module-scope `eventStore`/`pool`, none of which care that the React tree is gone. The
event is signed and broadcast. Only the `setPublished` / `setPublishEntry` call no-ops.

**CR-02 — `useMount` cannot register teardown.** Verified in `node_modules/react-use/lib/useMount.js`
this session: it is `useEffectOnce(function () { fn(); })` — the callback's return value is
**discarded**. `MinePOW` has no `useUnmount` and no other teardown. Worker termination therefore has
exactly three triggers, all requiring the component to stay mounted: the Cancel button (line 136), the
Skip button (line 145), and `cleanup()` on completion (line 47).

`node_modules/react-use/lib/useUnmount.js` exists and is already used at **four sites** in this repo —
`src/providers/local/intersection-observer.tsx:44` and `:99`, `src/components/lightbox-provider.tsx:80`,
`src/views/articles/components/article-reader.tsx:139`. Two of them import it alongside `useMount` from
the same module, which is exactly the shape this plan needs. There is no new dependency and no new
convention.

**Why the unmount path is reachable today.** `post-modal/index.tsx:303` renders
`<Modal isOpen={isOpen} onClose={onClose} size="4xl">` — it sets neither `closeOnEsc` nor
`closeOnOverlayClick`, and both default to `true` in Chakra v2 (measured: `@chakra-ui/react` 2.10.10).
The modal renders `ModalCloseButton` only when `publishEntry` is set (line 306), so during mining
**ESC or an overlay click is the only way out of the modal**. Each leaked worker sits in `miner.ts`'s
unbounded `setTimeout(mine, 0)` loop (line 33) with no exit condition other than finding the target,
across `navigator.hardwareConcurrency` threads, until the page is reloaded.

**Double-teardown is safe.** After a completed mine, `cleanup()` (line 47) has already terminated the
workers; the unmount teardown added by Task 1 then calls the same closure a second time.
`Worker.terminate()` is specified as a no-op on an already-terminated worker, and `clearTimeout` on an
already-fired handle is likewise a no-op. The executor does not need to guard against either.

**CR-01 — the failure is silent by construction, and the review's proposed fix is incomplete.**
`short-text-form.tsx:139` sets `setLoading("Signing and publishing note...")`. On the PoW path
`publishPost` is invoked from `MinePOW`'s `onComplete`/`onSkip` (lines 181-182) — *after* `submit`'s
`finally { setLoading(""); }` at line 151 has already run. Nothing else clears `loading`.

`publish` is `publishEvent`, whose `quite` parameter **defaults to `true`**
(`src/providers/global/publish-provider.tsx:140`). Its catch at lines 166-169 toasts the error and
returns `undefined`; it rethrows only when `quite` is false. So `publishPost` does not throw — it
returns with `pub === undefined` and `setPublished` is never called.

Render-gate order then traps the component: `published` (157) is unset, `loading` (165) is still set,
so the spinner renders forever and the `miningTarget && draft` gate (174) is never reached. `MinePOW`
has already unmounted, so there is no Cancel, no Skip, no retry and no form. Leaving the page is the
only escape — and `useCacheForm`'s teardown (`use-cache-form.ts:54-63`) and its `useBeforeUnload`
handler (66-77) both **remove** the localStorage entry when `isSubmitted.current` is true, which
react-hook-form sets as soon as `submit` resolves, i.e. immediately after `setMiningTarget`. Escaping
the spinner destroys the note.

**The review's suggested remedy — clear `loading` and fall back to the form — is necessary but not
sufficient, and shipping it alone would introduce a worse bug.** With `loading` cleared and `published`
unset, the next gate is `miningTarget && draft`, and on the PoW path **both operands are still
truthy**. `MinePOW` would remount, mine again, publish again, and loop indefinitely. The fix must also
release `miningTarget`. Task 2 does; do not "simplify" it back to the review's shape.

**Why `quite: false` is the wrong remedy for CR-01.** Passing `quite: false` would make `publishEvent`
rethrow — but on the PoW path the caller is a timer callback inside `MinePOW`, not an event handler,
so the rejection would be unhandled and the user would be no better off. The provider **already toasts
unconditionally**, before it decides whether to rethrow (lines 166-169), so the user-facing error
surface is identical either way. The in-repo precedent confirms the distinction:
`src/views/new/poll/poll-form.tsx:176-188` does pass `quite: false` — and it is safe there precisely
because it sits inside `useAsyncAction`, which catches and toasts. Task 2 therefore keeps the default
and treats `undefined` as the failure signal.

**WR-02 — the success screen can render before mining starts.** `bestProgress` is seeded at
