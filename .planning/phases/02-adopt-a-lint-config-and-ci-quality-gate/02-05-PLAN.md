<objective>
Calibrate the CI gate's `ci.failBelow` from measured scores of real commits, then record the one-time whole-repo baseline under the final adopted config.

Purpose: D-02 forbids picking a threshold up front. It must sit just under what typical real changes already score, and it must account for inherited findings in legacy files, which RESEARCH Pitfall 1 shows are usually the real blocker. D-04 records the whole-repo score once, not in CI, so backlog phases 999.2 to 999.10 have a baseline measured against the standard this phase adopted. The report must say plainly that it is not comparable to the 2026-08-02 scan.

Output: calibrated `ci.failBelow` in `.aislop/config.yml`; new `.planning/research/aislop-scan-{baseline-date}.md` (baseline plus calibration evidence) and `.planning/research/aislop-scan-{baseline-date}.json` (raw scan). `{baseline-date}` is the `date +%F` value when Task 1 starts, and both tasks use that same value.
</objective>

  The sample set is fixed. Every commit below was picked at planning time from real history and is a non-merge commit:
  - 774a08dfc — fix: NWC list_transactions permission (1 file)
  - a8cce223b — fix(signin): ncryptsec prompt wording (1 file)
  - 2af456d3f — feat: napplet history filter helper and hook (2 new files)
  - 770b031f5 — feat: napplet version history drawer (1 new file)
  - 82fefe8eb — feat(01-06): MutedUserCard and Private mutes section (2 files)
  - 47e98ab64 — Fix mute filtering in notifications (4 legacy service files)

  For each sample C:
  1. Create a detached worktree at C's parent: `git worktree add --detach "$WT" C^`, with WT under OUT.
  2. Symlink the main checkout's node_modules to `$WT/node_modules`.
  3. Copy CFG to `$WT/.aislop/config.yml`, run `git -C "$WT" add .aislop/config.yml`, then `git -C "$WT" -c commit.gpgsign=false commit -m calibration-base`. Record that commit as BASE.
  4. Run `git -C "$WT" -c commit.gpgsign=false cherry-pick C`. HEAD versus BASE is now exactly C's change, with the adopted config tracked and unchanged.
  5. From inside `$WT`, run `"$AISLOP" ci --changes --base "$BASE" --format json`, write stdout to `$OUT/C.json`, and record the exit code.
  6. Run `git worktree remove --force "$WT"`.

  If a cherry-pick conflicts, record the conflict, run `git -C "$WT" cherry-pick --abort`, remove the worktree, and continue with the next sample. After the loop, run `git worktree prune`.

  For each sample, record:
  - short SHA and subject
  - number of files scored
  - score, error count and warning count
  - each error's rule, file, and change context (new in the diff, or pre-existing in a touched file)
  - any security-engine findings
  - exit code under failBelow 70

  Gate-risk stop condition: if a sample that does not touch package.json or pnpm-lock.yaml reports a security-engine (dependency audit) finding at error severity, stop before changing failBelow and report it as a blocker. A project-wide audit finding would fail every change regardless of score, and changing `security.audit` is outside D-05 and D-09.

  Also record two long-lived-branch data points, but keep them out of the selection rule (RESEARCH Pitfall 8: such diffs are not typical changes). Run both before editing any file. From the main checkout HEAD, run `"$AISLOP" ci --changes --base origin/master --format json`. If a local `gh/master` ref exists, also run it with `--base gh/master`: that is the base GitHub Actions uses when this branch is pushed to GitHub (RESEARCH Pitfall 7). Record score, errors, exit code, and changed-file count for each. Together they are the expected first CI result, and the plan 02-02 end-of-phase human check compares against the gh/master figure.

  Selection rule for failBelow ("just under what typical changes already score", D-02):
  1. Take the scores of all measured samples.
  2. If the lowest score is at least 15 points below the second-lowest, set it aside as an outlier. Set aside at most one, and record its reason.
  3. The typical floor is the lowest remaining score.
  4. failBelow is the largest multiple of 5 strictly below that floor. Examples: floor 92 gives 90, floor 90 gives 85, floor 100 gives 95.

  Do not change any rule severity, exclude entry, or engine setting to make samples pass (D-05, D-09). Samples that fail only on inherited error-severity findings are expected ratchet friction: report them, do not tune them away.

  Edit only the `failBelow` line in `.aislop/config.yml`. Set the chosen number and add a trailing comment of the form `# calibrated {baseline-date} from sampled commits (aislop 0.16.1), evidence in .planning/research/aislop-scan-{baseline-date}.md`.

  Create `.planning/research/aislop-scan-{baseline-date}.md` with the title line `# aislop scan report — {baseline-date}` and a `## CI gate calibration` section; Task 2 adds the baseline sections above that section. The calibration section contains:
  - the method: worktree at the parent plus a config commit, cherry-pick, then `ci --changes --base`
  - a table with columns SHA, Subject, Files scored, Score, Errors, Warnings, Error rules (context), and Passes at chosen failBelow. A sample passes when its score is at or above failBelow and it has zero errors.
  - the selection rule, any outlier set aside, and the chosen value
  - the number of samples that fail only because of inherited errors, with the files named
  - the two long-lived-branch data points
