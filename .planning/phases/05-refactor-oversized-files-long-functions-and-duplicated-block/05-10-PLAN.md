<objective>
Promote the napplet shell's permission state and relay-tier helpers out of the 1162-line provider
into their own service modules, and close the one place where the provider reaches past the
permission API into its underlying map.

Purpose: D-08 requires the adapters be promoted into `src/services/napplet-shell/*` with a thin
provider left behind. This plan takes the cross-region state first, because RESEARCH.md found that
several regions read and write it and a later plan that moved a region without settling ownership
would have to duplicate it. CONCERNS.md prescribes exactly this — keep permission storage and grant
decisions in pure functions with unit tests — and D-15 depends on it.

Output: two service modules with fully encapsulated state, and a provider that no longer touches a
raw map.
</objective>

  <action>
Add a capability revocation function to the permissions module, beside the grant, that takes a
napplet identity and clears its entry from the approved capability map. Then change the consent
response callback's deny branch to call it instead of reaching into the map.

This is the one place in the split where the provider bypasses the permission API. If the map were
exported so the provider could keep deleting from it directly, the module's encapsulation would be
nominal — any module could then mutate granted capabilities without going through a named function,
which is exactly the property CONCERNS.md asks for and D-15 intends to test.

The revocation must clear the identity's entry completely, matching the current delete's behaviour
exactly. Do not take the opportunity to make it remove individual capabilities, or to also clear
the always-allow entry, or to call into the runtime's own access-control state. Any of those would
change the capability model while wearing the appearance of a refactor. The deny path today
clears the whole recorded set and touches nothing else; the replacement must do the same.

Land this as its own commit, separate from Task 1's move, and say in the message that it is a
behaviour-preserving encapsulation change rather than a pure move. That separation is what D-16
exists for — it lets a reviewer verify Task 1 mechanically as "nothing changed but location" and
then read this much smaller diff on its merits.
  </action>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| sandboxed napplet -> host capability check | An app's access to host capabilities is decided entirely by this module's recorded grants |
| browser storage -> persistent grants | The always-allow list survives reloads and is read back without further prompting |
| provider -> permission state | Previously the provider could mutate the grant map directly; this plan closes that path |

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-05-34 | Elevation of Privilege | capability grant bypass via direct map access | high | mitigate | Both maps stay unexported and every mutation goes through a named grant or revocation; the acceptance criteria assert no exported map declaration and no direct delete call in the provider |
| T-05-35 | Elevation of Privilege | capability check defaulting open after relocation | high | mitigate | The check's missing-entry-yields-false semantics are preserved verbatim under D-16's move-only rule, and the comment explaining that the underlying runtime defaults permissive travels with it so the reason for the closed default is not lost |
| T-05-36 | Tampering (silent loss of user grants) | always-allow storage key | high | mitigate | The key string is asserted unchanged and unique repo-wide; only the code that reads and writes it moves file |
| T-05-37 | Elevation of Privilege | over-broad revocation semantics | medium | mitigate | The revocation is constrained to clear exactly the recorded set, matching the current deny path; the plan forbids it from also touching always-allow or the runtime access-control state |
| T-05-38 | Denial of Service | window identity map reachable from two owners | medium | mitigate | The registry has exactly one owning module with explicit accessors, so the provider's frame lifecycle and the resource service extracted in plan 05-11 cannot diverge |
</threat_model>
