  <action>
The body renderer is a three-way branch whose arms have very different sizes. Extract each arm as
a module-scope PascalCase component and reduce the renderer to selecting among them.

The published-entry arm and the mining arm are small and take few inputs — the entry and a close
handler for the first, the draft, the target difficulty and three callbacks for the second. Extract
both as straightforward components.

The composer arm is the large one and closes over many values from the modal body. Pass it what it
needs as an explicit props object rather than trying to reduce it to two or three parameters; the
form object and a small set of callbacks cover most of it. The exact prop decomposition is yours —
D-12 leaves the shape of this extraction to discretion — but the composer component must end up
under the plain-function budget and must be declared at module scope.

Declare all three at module scope. Do not declare a component inside the modal component's body:
React remounts such a component on every render, which would reset the composer's focus and
in-progress state on every keystroke. This is the one way this task could introduce a real
regression, so it is a hard constraint rather than a style preference.

Once the three arms are components, the renderer collapses to a three-way selection. Either keep it
as a small function or inline the selection at its single call site in the modal content — both are
acceptable since it is called exactly once.

Preserve the branch conditions exactly. The published-entry branch keys off the publish entry, and
the mining branch off both the mining target and the draft being present. Phase 4 landed lifecycle
fixes in this path after a dormant mining code path was revived and exposed three defects, and the
two-operand mining condition is part of that fix — restating it as a single-operand check would
reintroduce a re-mine loop.

  <action>
The request handler is a single switch over eight methods. It divides cleanly by concern: five
methods operate on the app's update stream — sending an update, setting the update listener,
getting all updates, sending to chat and importing files — while three manage realtime channels,
joining one and sending or leaving on an existing one.

Split it into two handlers along that line and reduce the original to a dispatcher that tries the
update handler, then the realtime handler, and falls through to the method-not-found error when
neither claims the method.

Keep both handlers inside the component. They close over the post function, the webxdc instance ref
and the realtime channel map; the channel map in particular is a ref declared after the effect that
uses it, so hoisting the handlers to module scope would break their access to it and force
threading every dependency through parameters. Declaring them inside the effect as today, or
lifting them to memoised callbacks in the component body, both work — that choice is yours.

Preserve exactly:

- The outer message listener's guards. The origin equality check, the source-window check and the
  protocol version check all gate untrusted frame input and must not move into a helper or be
  loosened while the code around them is rearranged.
- Every error code and message string, including the method-not-found code used for both an
  unknown method and an unsupported realtime capability.
- The single catch around the whole dispatch that converts a thrown error into an error response.
  It must still cover all eight methods after the split, not just one handler.
- The existing linter suppression comment above the handler's signature — carry it with whichever
  signature keeps the loosely typed parameter.

Do not change the ready-and-initialise path at lines 112-129 or the imperative handle above it.
