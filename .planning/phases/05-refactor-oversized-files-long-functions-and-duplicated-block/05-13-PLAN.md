<objective>
Add a unit-test runner scoped to the pure functions this phase extracted, and prove the napplet
permission decisions behave as intended.

Purpose: D-15 deliberately overturns the Phase 3 decision that rejected a test framework as its own
phase. The justification is specific: this phase relocates roughly 1,750 lines of behaviour-bearing,
zero-coverage code, where the type checker proves types but nothing proves behaviour. CONCERNS.md
prescribes exactly this — keep permission storage and grant decisions in pure functions with unit
tests — and the D-08 split is what finally makes them testable. D-17 places the harness last for
that reason: before the split there was nothing pure to test.

Output: a standalone runner, a test script, and focused tests on permissions and wallet mapping.
</objective>

Install the approved version as an exact-pinned development dependency, using the package manager's
save-exact flag so the manifest records a bare version with no range prefix. This follows the
exact-pin precedent already set by the lint tool's entry in this manifest.

Create `vitest.config.ts` at the repository root. Keep it standalone and minimal: a node test
environment and nothing else. Do not extend the application build config and do not add a test block
to it — that config wires a React plugin, a progressive-web-app plugin that scans the service worker
source and injects a manifest, and a path-resolution plugin, none of which a unit test over pure
functions needs, and the manifest injection is a plausible source of flakiness in a collection run.

Do not enable global test APIs. Import the test functions explicitly in each test file instead. The
type configuration in this project has no types array today, and enabling globals would mean adding
one purely to satisfy the runner.

Add a `test` script that runs the runner once and exits. It must not be a watch-mode invocation —
the planning test command runs it unattended.

Write the first test file beside the module it covers, at
`src/services/napplet-shell/permissions.test.ts`. Cover the behaviour that matters:

- The identity key composes the three identity fields into a stable string, and two identities
  differing in any one field produce different keys.
- An identity with no recorded grant reports **false** for any capability. This is the single most
  important assertion in the phase: the comment carried into that module explains that the
  underlying runtime defaults to a permissive policy, which is exactly why this module's own record
  must default closed.
- After granting a capability set, the check reports true for a granted capability and false for one
  that was not granted.
- After revoking, the check reports false again for a previously granted capability.
- Revoking an identity that was never granted anything is a no-op and does not throw.
- The always-allow round trip: an identity added to the list is subsequently reported as
  always-allowed, and one that was never added is not.

Two practical notes the research did not resolve. First, the grant function takes the shell bridge
and calls into the runtime's access-control state, so pass a minimal fake bridge and assert it was
called with the identity's fields — that keeps the test honest about the side effect rather than
pretending the function is side-effect-free. Second, the always-allow trio reads and writes browser
storage, which the node environment does not provide; install a minimal in-memory storage stub on
the global object in this test file, and reset it between tests. Keep the node environment rather
than switching to a browser-like one for this single dependency.

Finally, flip the planning test command from the build to the test script.

Land every one of these in a **single commit**: the dependency and lockfile, the runner config, the
package script, this test file, and the planning test command. Flipping the planning command before
a test file exists makes the runner exit with no test files found, turning the per-task gate red for
reasons unrelated to the work in that task.

Leave the build command as it is. It remains the separate, always-applicable type-check gate that
D-19 requires after every task.
