<objective>
Replace the per-origin (per-Blossom-server) network prompt for napplets with one gate. If the user approved the NAP-RESOURCE capability (`resource:fetch`) in the normal napplet consent modal, the napplet may download Blossom blobs from any server.

Purpose: The user asked for this in these words: "if the user approves just the nap-resource permission then the napplet can download resources from blossom servers". Today `createResourceService` in `src/providers/global/napplet-shell-provider.tsx` allows an origin only in three cases. First, it is one of the active account's Blossom servers (kind 10063 list). Second, it is in a localStorage "always allow" list keyed per napplet identity plus origin. Third, the user picks "Allow once" or "Always allow" in an "Allow network access?" modal shown for each new origin. The approval in the consent modal never enters into it. So napplets that fetch blobs from Blossom servers outside the user's list get prompted once per server. This plan removes all of that per-origin machinery. Downloads are now gated on the capability the user already approved, plus a check that the URL is a Blossom blob URL.

Output: A rewritten resource gate in the shell provider with the per-origin types, storage helpers, provider state, callbacks and modal deleted. Plus a patch changeset.
</objective>

Why the runtime ACL cannot be the gate (verified in node_modules/@kehto/runtime/dist/index.js and @kehto/acl/dist/index.js):
- `createRuntime` builds its ACL with `createAclState(hooks.aclPersistence, "permissive", ...)`.
- For an identity with no entry, `check()` returns `state.defaultPolicy === "permissive"`, i.e. true.
- `aclState.grant()` calls `ensureRuntimeDefaultEntry` first. Under permissive policy that seeds the entry with every capability (`RUNTIME_CAP_ALL`) before adding the requested one.
- The runtime gates `resource.bytes` / `resource.bytesMany` / `resource.info` / `resource.cancel` on sender capability `resource:fetch` (`resourceMap` in @kehto/acl). Given the two points above, that check always passes. `bridge.runtime.aclState` therefore cannot tell whether the user approved `resource:fetch`. The shell has to keep its own record of the approved list.

Consent flow (src/components/napplets/napplet-frame.tsx lines 97-116, 167-172):
- `const capabilities = getNappletRequiredCapabilities(active);` builds the list from manifest `requires` tags. `requires resource` maps to `["resource:fetch"]`.
- `requestConsent(active, { pubkey: active.pubkey, dTag: resolved.dTag, aggregateHash: resolved.aggregateHash }, capabilities)` runs before the frame mounts. If it resolves false, the frame never mounts.
- `registerFrame(windowId, node.contentWindow, { pubkey: active.pubkey, dTag: napplet.dTag, aggregateHash: napplet.aggregateHash, title })` uses the same triple, so `identityKey()` keys agree.

Existing shell-provider pieces to reuse (src/providers/global/napplet-shell-provider.tsx):
- `type NappletIdentity = { pubkey; dTag; aggregateHash; title? }` and `identityKey(identity)` returns `${pubkey}:${dTag}:${aggregateHash}`.
- `grantCapabilities(bridge, identity, capabilities)` is called from `requestConsent`'s auto path (always-allowed, or empty capability list) and from `respond(true, ...)`.
- `windowIdentities` is a module-level map from windowId to identity, filled by `registerFrame` and cleared by `unregisterFrame`.
- `sendResourceError(send, requestId, "denied", message)` maps to NAP error `blocked-by-policy`.
- `Capability` type is already imported from `@kehto/shell`.

Blossom URL helper already used in this codebase (src/components/content/links/video.tsx):
- `import { getHashFromURL } from "blossom-client-sdk";`. `getHashFromURL(url: string | URL)` returns the last 64-hex sha256 found in `url.pathname`, or `null`.

aislop baseline for src/providers/global/napplet-shell-provider.tsx (measured while planning): 0 errors, 20 warnings.

## STRIDE Threat Register

| Threat ID | Category | Component | Severity | Disposition | Mitigation Plan |
|-----------|----------|-----------|----------|-------------|-----------------|
| T-q7c-01 | Elevation of privilege | `fetchOne` in createResourceService | high | mitigate | The kehto ACL is permissive, so its `resource:fetch` gate always passes. `fetchOne` therefore checks `hasApprovedCapability(identity, "resource:fetch")` against the `approvedCapabilities` record that `grantCapabilities` writes only after user consent (the modal, or a stored "Always allow"). A same-session deny clears the record. |
| T-q7c-02 | Information disclosure | shell-side `fetch()` of napplet-chosen URLs | medium | mitigate | Only http(s) URLs that `getHashFromURL` recognises as Blossom blob URLs are fetched. Anything else gets `blocked-by-policy`, so the shell no longer fetches arbitrary endpoints after a one-click approval. |
| T-q7c-03 | Information disclosure | napplet beaconing data to a server of its choosing via a Blossom-shaped URL | medium | accept | The user asked for exactly this: approving NAP-RESOURCE covers every Blossom server. The consent modal lists `resource:fetch` before approval, and a napplet without that approval cannot fetch at all. |
| T-q7c-04 | Denial of service | large or many fetches | low | mitigate | `MAX_RESOURCE_BYTES` (25 MiB), `MAX_RESOURCE_URLS` (16) and `MAX_CONCURRENT_RESOURCE_FETCHES` (4) stay in `fetchOne` and `resource.bytesMany` unchanged. Per-window abort on destroy also stays. |
| T-q7c-05 | Tampering | server returns bytes that do not match the URL's sha256 | low | accept | Behaviour is the same as before, since the shell never verified hashes. Verifying would break HEAD and range requests a napplet may make. A napplet that needs integrity can hash the returned blob itself. |
